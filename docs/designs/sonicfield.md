## Vision (Aspirational — not MVP scope)

### 10x Direction
SonicField's long-term ceiling is the spatial audio OS for live sports globally: multiple sports,
broadcaster partnerships, eventual first-party hardware integration. This section is directional
only — no engineer should anchor MVP decisions on it.

### Platonic Ideal (12-month target, not v1)
A product that makes acquired-blind sports fans say "I'm THERE" — the pitch is a sensory space,
not an information feed. Crowd roar pans from the scoring end. On-device CV runs offline. A sighted
friend watching alongside can understand exactly what their blind companion is experiencing.
Note: on-device CV is a 12-month aspiration. v1 uses server-side CV.

## Accepted Scope (added to MVP plan)

- **Crowd Spatial Roar**: Extract crowd audio from broadcast stream using source separation
  (Demucs or equivalent ML model, server-side); pan directionally to scoring end at goal events.
  ~1 week of additional work; not included in Gate 1 validation.
- **Earcon Playground**: Interactive pitch with movable virtual ball; user hears earcons at any
  pitch position; learn spatial audio before first live match. 4th screen in app.

## Deferred to TODOS.md

## Core Architecture Plan

### Platform Decision: Web First
Web Audio API on browser (fastest to ship, most accessible for screen readers).
Mobile wrapper (React Native or PWA) is v2.

### Data Pipeline (Hybrid — explicit risk-ordered)

**EXISTENTIAL RISK**: K-League real-time event API availability and cost is unknown.
K-League data is not commoditized like Premier League. Must be resolved in Week 1 before
any pipeline work begins. Fallback: start with a league that has a known affordable API
(e.g., StatsBomb open data for historical; Sportradar trial for live PL/La Liga).

Priority order:
1. Events (goal, foul, penalty, corner, substitution): cheap event APIs.
   K-League API availability = open question to resolve FIRST.
2. Spatial ball tracking: YOLO-based CV on server-side (not on-device) from broadcast stream.
   Latency: ~200-500ms. Acceptable for spatial audio (not real-time gaming). Test this.
3. Crowd audio (post-Gate-2): FEASIBILITY RISK. Demucs and similar source separation models
   operate with multi-second processing windows — real-time extraction from a live stream is
   likely not achievable at <2s latency with current open-source models. Alternative approach
   to evaluate first: rather than separating crowd from broadcast, detect crowd-roar audio
   energy peaks (simpler signal processing, no ML) and pan the full broadcast crowd audio to
   scoring end at goal events. Test this simpler approach before committing to Demucs.
   Crowd audio feature is gated on feasibility spike (1 day) after Gate 2.

### Audio Engine
- Web Audio API, `PannerNode` with `panningModel: 'HRTF'` (browser built-in) for binaural panning
- 5 earcons (locked set for v1): goal chime, foul whistle, tackle thud, corner ping, penalty buildup
  Audio characteristics: each earcon 200-800ms duration, distinct frequency range, no overlap.
  Source: design 3 candidates per earcon type; validate in Gate 2 for recognizability.
- Substitutions: no spatial position — fire as stereo center notification sound, not panned
- Headphone profiles: DEFERRED to v1.1. Browser built-in HRTF is the baseline.
  If Gate 2 shows significant quality gap across headphone types, add ConvolverNode-based
  compensation in v1.1 using MIT KEMAR HRTF dataset (open license) for custom convolution.
  Note: PannerNode HRTF (built-in) and ConvolverNode (custom) are different signal chains;
  do not attempt to combine them — pick one approach per audio path.
- Earcon audio file spec: 48kHz, stereo WAV, < 1MB each; pre-loaded at app start

### Screens (5 total)

Pitch grid orientation: 5 columns (left to right = pitch width) × 3 rows (top to bottom = near end
to far end). Column 1 = hard left, Column 3 = center, Column 5 = hard right. Row 1 = near end,
Row 3 = far end. Audio pans accordingly: columns drive left/right pan, rows drive front/back depth.

1. **Game Select** — live games list, K-League primary (fallback: Premier League if K-League
   API unavailable per Gate 0); "Start Listening" CTA
   - Error state: "No live games right now" with next scheduled match time
   - Error state: API unavailable — show cached last-known schedule with stale indicator
2. **Active Listening** — 5×3 zone grid showing ball zone indicator dot; earcon legend below
   grid with per-type mute toggle (tap earcon name to mute/unmute); Stop button
   - Error state: CV tracking lost — earcons continue from event API, ball dot freezes, banner shown
   - Error state: Event API lost — "Live connection lost, earcons paused" banner; ball dot still
     moves if CV is alive
   - Fallback: both lost — offer "Switch to commentary only" which mutes SonicField audio
3. **Earcon Onboarding** — 5 earcons in fixed sequence; each step: earcon name + description +
   Play Sample button; Next enabled only after play. Progress: "2 of 5". Skippable at any step.
   Effort: ~1 day. (Scope table omitted this; adding: ~1 day / ~1 hr)
4. **Earcon Playground** — 5×3 grid; tap any cell to fire current earcon panned to that zone;
   earcon selector at bottom (tap to cycle: goal → foul → tackle → corner → penalty → goal).
   No time pressure. "Back to games" link.
5. **Settings** — language toggle (KO/EN; applies to all UI text and onboarding labels;
   earcon audio files are non-verbal so no localization needed); Onboarding reset; About.
   Headphone profile selection: DEFERRED to v1.1 (see Audio Engine note above).

### Auth / Session
No login required for v1. Browser-local state (muted earcon types, language preference).
If usage analytics needed: anonymous session ID only. No PII collected.
Blind user accessibility: all interactive elements must have ARIA labels; keyboard-navigable;
no time-limited interactions.

## Validation Gates (sequential — each blocks the next)

**GATE 0 (Days 1-3)**: K-League API + broadcast rights + CV cost research.
IMPORTANT: Gate 0 is information-only. No pipeline code starts, no infra spun up, no CV
approach committed until Gate 1 (user demand) passes. Research is reversible; architecture is not.
Three parallel tracks:
- Track A: K-League event API — contact Sportradar (trial account), StatsBomb, direct K-League
  data partnership. Pass = specific API confirmed with cost <$200/month and latency <2s.
  Fallback league if fail: English Premier League (Sportradar trial is available).
- Track B: Broadcast rights legal check — confirm whether server-side CV processing of a
  broadcast stream constitutes a rights violation. Most leagues prohibit rebroadcast but
  CV analysis of a personally-received stream is a grey area. Consult a media rights advisor
  or find precedent (e.g., how other CV sports startups handle this). If rights are blocked,
  CV approach must be replaced with API-only (no spatial ball position, events only).
- Track C: Server-side CV compute cost spike — estimate GPU instance cost, YOLO inference
  time per frame, and cost per concurrent user at MVP scale. Use AWS/GCP pricing calculator +
  published YOLO inference benchmarks. If cost exceeds $5/user/match at target scale, CV
  architecture needs a rethink before any pipeline work begins.
Pass = all three tracks resolved with a clear path forward (even if fallback is required).
Timeline: 2-3 days. This is business development, legal research, and cost modeling — not a 2-hour task.

**GATE 1 (Week 1)**: User discovery — blocks architecture decisions.
Talk to 3 actual acquired-blind sports fans (Korea preferred; international acceptable).
Deliver: name, sport they follow, what they currently do to follow matches, specific frustration.
Pass = at least 2 of 3 confirm: (a) audio commentary alone is inadequate, (b) they would try
a spatial audio alternative, (c) they own or would buy spatial-audio-capable headphones.
Rationale: user discovery gates architecture. If the problem is not confirmed, do not build.

**GATE 2 (Week 2, ~2 days)**: Spatial encoding validation.
StatsBomb historical data + Web Audio API PannerNode (built-in HRTF, no custom profiles yet) +
one HTML page. 5 earcons, 10-minute match segment, scrubable timeline.
Test with 3 participants wearing headphones (sighted is acceptable; acquired-blind preferred
if contacts from Gate 1 are willing).
Blind-user adaptation: replace visual pitch diagram pointing with verbal zone description
("left side near goal / center / right side near goal"). Sighted participants may use diagram.
Pass (static test) = 2/3 participants correctly identify which third of the pitch
(left/center/right) the last 5 shots came from.
Stress-condition sub-test (added): at session end, play 3 consecutive events at live match
cadence (no pause between earcons). Ask user to identify where the last event occurred.
Pass (stress test) = 2/3 correct. Tests whether users maintain orientation under real
match pressure — static test alone doesn't reveal this.
Cross-browser HRTF test: run the same 5-earcon sequence in Chrome and Firefox. If Firefox
spatial quality is notably degraded, add browser recommendation UI to app start screen
(non-blocking, informational: "For best spatial audio, use Chrome or Safari").
If fail: test familiar sonic metaphors (ball physics sounds, directional ambient crowd) vs.
designed earcon grammar. Do not commit to earcon design until this is resolved.

## Open Questions (resolved after Gates 0-2, before full architecture is locked)

1. K-League API: provider, cost, latency → GATE 0 Track A resolves; fallback = PL
2. Broadcast rights for server-side CV → GATE 0 Track B legal track resolves
3. Server-side CV compute cost at scale → GATE 0 Track C cost spike resolves
4. Earcon grammar vs. familiar sonic metaphors → GATE 2 resolves
5. CV ball tracking latency: server-side YOLO test on sample broadcast video; p99 measure
6. Crowd audio: energy-peak detection (simple) vs. Demucs source separation (complex) —
   run 1-day feasibility spike after Gate 2; pick approach based on latency results
7. Localization depth: UI text only (KO/EN) is straightforward; audio narration in onboarding
   would require recorded audio files in both languages — defer audio narration to v1.1
8. Screen reader testing: VoiceOver (iOS/macOS) and NVDA (Windows) are the two required.
   All 5 screens must pass screen reader navigation before launch; add to pre-launch checklist.
9. TAM note: Gate 1 pass criteria explicitly asks about headphone ownership/willingness to buy.
   If users confirm intent but lack hardware, addressable market is "acquired-blind sports fans"
   (not the subset who already own spatial-audio headphones) — a meaningfully larger number.

## Error Handling Requirements

Every data dependency has an explicit degradation path:
- K-League API down: cached event list + stale indicator; no spatial earcons during outage
- CV tracking lost: earcons continue (event API), spatial panning freezes at last known position
- Both event API + CV lost: offer broadcast commentary audio only mode
- Audio device not detected: prompt to check headphones before starting; no silent failure
- Spatial audio not supported by browser: warn user, offer mono fallback with L/R panning only

## What NOT In Scope (v1)

- Haptic feedback (requires hardware)
- Multi-sport (football/soccer only)
- Stadium/venue mode
- Social/sharing features
- AI commentary layer (this makes it a better radio, not a TV)
- On-device CV (server-side only in v1)
- Developer SDK
- Native mobile app (web-first; PWA wrapper is v2)
